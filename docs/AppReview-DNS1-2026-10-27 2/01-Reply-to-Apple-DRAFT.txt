Thank you for the detailed findings under Guideline 2.5.19. For version 1.1.0, build 6, we believe the three findings correspond to our custom backend-discovery component, internally named DNS1.

1. Remote server lookup
The user enters an invitation code on the club connection screen. DNS1 uses that code to locate the corresponding messaging backend. It also supports connection recovery. We acknowledge that endpoint addresses are retrieved remotely and can change.

2. Decoding server addresses
DNS1 uses a custom protocol: it reconstructs endpoint data carried in AAAA records. If the DNS sources cannot provide a usable node, it can download and decrypt a fallback BIN file. The parser extracts TCP host/port entries and optional HTTP URLs. TCP entries are used to connect to the messaging service; HTTP URLs supply API and file-transfer endpoints. This parser does not interpret feature flags, page definitions, executable code, or commands to enable hidden functionality. Additional JSON fields are not consumed by this parser.

3. Lookup credentials
The account identifier, access key and request signature authenticate the DNS service request. The secret is used locally to calculate the signature; it is not included as a plaintext query parameter. These are separate from user login credentials and are not used by DNS1 to unlock app features.

4. Supporting source and data flow
The attached source appendix identifies DNS1DoHClient (lookup/signature), DNS1Payload (AAAA reconstruction and BIN decoding), DNS1NodeRaceCoordinator and DNS1SourceRace (source selection and connectivity probing), OSSConnectionBootstrap (endpoint consumers), and AesEncryptUtils (BIN decryption helper). Actual lookup credential definitions are excluded; the implementation logic remains visible.

The attached technical note describes the accepted fields and connection flow. The attached DNS1-Live-Response-Evidence.pdf documents a live capture on 27 October 2026: 7 AAAA records decoded to 4 TCP nodes, while an independent BIN retrieval decoded to 4 TCP nodes and 4 HTTPS URLs. The TCP node sets matched. Addresses and ports are consistently redacted. The DNS result was originally a comma-separated list; the displayed JSON is normalized output.
